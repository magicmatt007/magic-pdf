# magic-pdf

A lightweight cross-platform PDF viewer and editor: Rust, PDFium (raw C API, loaded at
runtime) and egui/eframe. The README describes features, building and packaging.

These rules apply to every session, local or in the cloud.

## Working with git

- Start from an up-to-date `master` (`git pull`); cloud sessions start from GitHub's
  `master`, so local work must be pushed or merged before switching to the cloud.
- Work on a branch and open a pull request into `master`. Do not push to `master`
  directly and never push tags.
- CI (clippy and tests on Linux, Windows and macOS) must pass. Merge only when the user
  says so.
- Never commit the user's own PDFs or other personal files. Test files live in
  `tests/fixtures/` and are generated by the scripts there.

## Releasing

Releases are made by merging a version bump; GitHub does the rest.

1. In the pull request, run `scripts/bump-version.sh X.Y.Z` (updates `Cargo.toml` and
   `Cargo.lock`, creates `release-notes/X.Y.Z.md`).
2. Write the "What's new" text in `release-notes/X.Y.Z.md`, in the style of the earlier
   files there: short bold section headings, one bullet per user-visible change, written
   for users (no code names).
3. When the pull request is merged, the *Release* workflow builds the Windows installer,
   the portable zip, the macOS disk image and the Linux AppImage, creates the tag
   `vX.Y.Z` and publishes the release with the notes at the top.

Version numbers: bump the minor version for new features, the patch version for fixes.
A test build without publishing: Actions → Release → Run workflow (publish unticked).

## Building and checking

```
scripts/fetch-pdfium.sh            # once: downloads libpdfium into third_party/
cargo test
cargo clippy --all-targets         # must be clean
cargo fmt                          # style from rustfmt.toml; CI checks it
```

- Every user-visible text goes through `t()`/`tf()` (`src/i18n.rs`) and needs a German
  entry in `src/i18n/de.rs` (Swiss spelling, "ss" not "ß"); a test fails otherwise.
- PDFium runs on one engine thread (`src/engine/`), driven by `Request`/`Response`
  messages. Changes PDFium cannot write (outline, metadata) go through lopdf
  (`src/engine/lopdf_ops.rs`).
- To look at the running app without clicking through it, the `MAGIC_PDF_*` variables
  (`MAGIC_PDF_SCREENSHOT`, `MAGIC_PDF_TOOL`, `MAGIC_PDF_LANG`, …, see the README) open a
  file in a given state, save a screenshot and quit.
